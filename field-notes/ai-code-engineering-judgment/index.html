AI / Engineering Judgment

AI Can Write the Code. Who Reviews the Engineering?

The new problem isn’t code generation. It’s knowing whether the generated system deserves to exist.

5 min read20 September 2026

AI can now generate substantial amounts of software extremely quickly.

That changes the developer’s problem. The difficult question is increasingly not:

“Can I write this?”

but:

“Should this be built this way?”

01

More output isn’t necessarily better.

AI can produce more code, more files, more abstractions, more documentation, more tests, more architecture and more features. All of it arrives at roughly the speed you can read the first line.

But output volume is not engineering quality. Every extra file is something to read. Every abstraction is something to maintain. Every test, dependency and feature is something that can break, be attacked, or have to change later.

Overproduction can become an engineering problem.

When producing code is cheap, the cost moves to everything after it: understanding it, verifying it, running it and owning it. Nothing about generation makes those costs smaller.

02

The AI black box.

Ask for an application and you can get a project structure that looks entirely reasonable:

It looks like engineering. But the developer who received it may not know:

  • Why these layers exist
  • Why these abstractions were introduced
  • Which dependencies matter
  • Which assumptions were made
  • Which patterns are actually necessary
  • What happens when something fails

The system appears to have materialized out of nowhere. The reasoning that produced it is gone, and the developer has to reconstruct it before they can judge it.

Observation
The structure has nine top-level folders.
Question
Which of them does this problem actually require?
How to check
For each layer, say what it separates from what. If you can’t, take it out on a branch and see what you lose.

Inspecting the reasoning behind an implementation is the habit we build in Build Lab. It’s why we use an Anti-Tutorial approach: the thinking stays visible instead of disappearing behind finished code.

03

Overengineering and underengineering.

A system can be wrong in two directions.

Underengineered

Too simple for its actual requirements.

  • Weak validation
  • Poor security
  • No meaningful failure handling
  • Insufficient observability
  • Fragile data handling

Overengineered

More complex than the requirements justify.

  • Unnecessary microservices
  • Excessive abstractions
  • Premature scaling
  • Unnecessary dependencies
  • A complicated architecture for a simple problem

Generated code drifts easily toward the second. More is the default output. So the judgment has to come from a person who knows what the requirements actually are.

Build the simplest system that adequately satisfies the actual requirements — and know when that simplicity must change.

04

The developer’s new job.

If the implementation is cheap, the questions around it are the job. A developer should increasingly be able to answer:

  1. Why this architecture?
  2. Why this database?
  3. Why this language?
  4. What assumptions are we making?
  5. What happens when this fails?
  6. Where are the trust boundaries?
  7. What happens at 10× scale?
  8. What happens if the requirements change?
  9. What did AI decide?
  10. Do we agree with that decision?

None of these are answered by the code. They’re answered by the person responsible for it.

05

Generated is not the same as understood.

AI-generated implementation still needs human comprehension, verification and ownership. Code that runs is evidence that something was produced. It isn’t evidence that anyone knows why it works, when it stops working, or what it quietly assumes.

The goal isn’t to reject AI. The goal is to use it without surrendering engineering judgment.

Next

What to question next.

Open the last thing AI generated for you. Pick one layer, one dependency and one decision you didn’t make. For each, write one sentence explaining why it’s there. Where you can’t, you’ve found what to investigate.

The developer still owns the decision.
