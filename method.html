Method

How we reason about systems.

Three habits that apply to any language, any framework and any AI tool: decide with reasons, treat security as part of the design, and never confuse generated with understood.

01 — Decisions

We don't care which language you choose.

We care whether you can explain why you chose it. The route from problem to code is the same whatever the stack.

  1. Problem
  2. Constraints
  3. Requirements
  4. Technology options
  5. Trade-offs
  6. Decision
  7. Implementation

Worked question

An order-tracking service for a small team. Data is mostly customers, orders and line items. Which database — and why?

PostgreSQL

Fits when

Data is relational, integrity matters and the questions you ask will keep changing.

Costs

Schema changes need discipline. Scaling writes horizontally is real work later.

Would change if

The data turns out to be document-shaped, highly variable and always read as a whole.

MongoDB

Fits when

Records are self-contained documents, read and written as a unit, and their shape varies.

Costs

Relationships and cross-document consistency become your job. Ad-hoc reporting gets harder.

Would change if

Requirements grow join-heavy, or integrity across records starts to matter more than flexibility.

“Whatever AI picked”

Fits when

Only when you've checked it against the requirements and reached the same answer yourself.

Costs

You inherit a decision with no owner and no recorded reason.

The test

Can you write the reason in one sentence? If not, the decision isn't made yet.

“Why MongoDB?” matters more than “Can you write a MongoDB query?”

02 — Security

Security is not a module. It's a way of reading a system.

We don't teach it as a checklist at the end. We ask the same six questions of every system from the first sketch.

SYSTEM

  • TrustWhat are the trust boundaries? What should never be trusted?
  • DataWhat data is sensitive? Where does it travel, rest and leak?
  • UsersWho uses this — and who can attack it?
  • Attack surfaceWhat can go wrong? How do we reduce the blast radius?
  • FailureWhat happens after compromise? How do we detect abuse?
  • RecoveryHow do we contain, revoke and restore?

03 — AI collaboration

Use AI as an implementation partner, not an authority.

AI is fast, tireless and often right. It is also confident when it's wrong. Ownership stays with you.

  • 01Interrogate

    Ask why the architecture looks this way. Make it justify each choice.

  • 02Verify

    Read generated code as if a stranger wrote it. Someone did.

  • 03Challenge

    Surface the assumptions it made silently, then decide which you accept.

  • 04Test

    Outputs are claims. Tests are how you check them.

  • 05Catch hallucinations

    Invented APIs, imaginary options, plausible nonsense. Check them against the docs.

  • 06Understand dependencies

    Every package it added is code you now depend on and must trust.

  • 07Inspect security

    Look at input handling, secrets, permissions and what happens on failure.

  • 08Simplify

    Generated code tends to add. Your job is often to take away.

  • 09Own

    Keep the decisions. If you couldn't defend it, don't ship it.

Never confuse generated with understood.

04 — Failure

Failure is where the reasoning becomes visible.

When a system breaks, the assumptions behind it come to the surface. We investigate in four moves.

  1. 01Reproduce

    Make it fail on demand. Until you can, you're guessing.

  2. 02Isolate

    Shrink the problem until only the cause is left.

  3. 03Explain

    State why it happens in plain language. If you can't, you haven't found it.

  4. 04Prevent

    Change the design or the checks so this class of failure is caught next time.
